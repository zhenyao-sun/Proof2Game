# Proof2Game 用户需求

## 1 产品与发布范围

Proof2Game 是面向数学稿件和笔记的开源工作系统。在 ChatGPT Desktop + Codex 中，它从用户给定的材料建立可恢复的游戏脚本，验证并推进完整证明，最后交付可分享的数学学习游戏。用户自己的未公开项目还可生成完整英文稿件。

- 首版提供第 2 节规定的引导模式，以及可独立调用的文献入库 `paper_ingest`、自动化脚本验证和手动重构 `refactor`。
- 制作端支持网页版 ChatGPT Work 的 Linux 工作区及 macOS 上的 ChatGPT Desktop/Codex。游戏游玩端使用 macOS 上的 Codex 启动。
- 游戏仅以托管网页形式分发，首版以 GitHub Pages 为部署目标。发布后，玩家通过网页链接进入。
- 首版省去另行组织的全文复审、章节结构图、论文导读、作者伴读反馈和轻量自动验证模式。公开文献的 Writer 审稿报告见第 9.4 节。
- 默认用中文交流，可按用户要求切换英文。稿件和数学审查报告使用英文，游戏支持中英文切换。
- 仅由面向用户的主会话在首次使用 Proof2Game 时检查实际加载的版本与其 GitHub 上游。Reviewer、Fixer 等内部会话统一沿用主会话为本次任务选定的版本。有可用更新即暂停，得到用户明确同意后才执行更新，并核对实际加载的版本。用户明确选择跳过时沿用已安装版本。已有可用安装而 GitHub 暂时不可达时，说明无法检查更新，使用已安装版本继续。其他检查失败或实际更新失败时，报告具体原因，保留状态并暂停。更新应保留研究原稿、工作区改动、审查记录、来源与暂停状态。

## 2 快速启动与使用引导

- 公开版 README 提供一段可直接复制的启动提示，标题为「把下面这段话发给你的 ChatGPT Desktop/Codex」。Agent 根据提示从 Proof2Game 的 GitHub 仓库自行下载完整系统，读取启动说明并开始引导用户。
- 数学项目文件夹未明确时，询问用户项目文件夹在哪。需要处理稿件而目标 manuscript 未明确时，询问用户稿件在哪。已有明确信息时直接沿用。
- 稿件相关功能以用户提供的现有 manuscript 或 math note 为输入，草稿也可以。若用户还没有稿件，引导模式应说明 Proof2Game 用于处理给定的数学稿件或笔记，并请用户先提供一份再开始。
- 首版接受 LaTeX、Markdown、PDF 或 arXiv 链接作为稿件输入。以用户指定的文件或链接指向的稿件为处理对象。对 arXiv 链接，获取其指向的稿件并记录实际版本及其公开日期。
- 目标原稿为 PDF 时，逐页渲染页面并通过图像识别忠实转录为 Markdown，再据此建立英文游戏脚本。用户直接提供和从 arXiv 下载的目标 PDF 均走此流程，原始 PDF 按原样保留。
- 收到已有稿件后，直接从原稿另建一份英文游戏脚本，无需先让用户确认结构。原稿按原样保留，包括中文原稿。统一使用英文游戏脚本进行数学审查和路线验证，保留原稿已有的论证并标出待补的缺口。
- 能从原稿明确判断主结果时，直接将其列入 Main Results 并建稿。仅当原稿存在会改变交付所含目标定理的实质歧义时，才请用户确认目标范围。
- 用户指定处理同一稿件的新原稿版本时，在另一个文件夹以该版本为输入新建游戏脚本。各原稿版本分别绑定自己的脚本、审查状态、检查点、Goal 和交付物。同一版本的任务恢复按第 3.1 节处理。
- 引导模式建立游戏脚本后，自动进入该项目类型对应的自动化脚本验证，无需用户再指定下一步。
- 自动化脚本验证通过后，两类项目都自动运行 `game_developer` 导出可部署的游戏网站。用户自己的未公开数学项目还会自动运行 `writer` 生成完整稿件。两项可并行执行，都使用同一份通过验证的交付快照。快照只包含仍在交付目标依赖范围内的组件。
- 公开文献项目验证通过后自动运行 `writer`，在内部比较目标原文与最终游戏脚本，生成针对原稿、面向作者的英文审稿报告。报告可与游戏导出并行，生成与检查均计入引导任务的完成条件。
- 公开文献项目因已核验的反例而经用户确认撤回最后一个目标定理时，引导模式转入仅交付硬伤报告的流程，见第 9.4 节。
- 用户自己的未公开项目经用户确认撤回最后一个目标定理时，保存现有工作和撤回决定，向用户说明撤回原因并结束本次任务。交付止于这项说明。
- 用户启动一次引导模式后，主 agent 持续协调，直至产出该项目类型对应的全部交付物。稿件摄取、脚本建立、探索、审查、修复、收尾审查和交付之间自动衔接。主 agent 可在关键节点汇报进度，汇报后直接推进。可恢复的执行问题由系统处理并接续。需要用户补齐必需输入或来源、给出具体授权或作出实质决定时，按对应规则保存状态并在受阻处等待，解除阻塞后自动接续。用户要求暂停时保留可恢复状态。

README 启动提示草案（发布时填入实际 GitHub 仓库地址）：

> 请从 GitHub 下载 Proof2Game（<Proof2Game 仓库地址>），阅读仓库的启动说明，然后引导我用 Proof2Game 处理已有的数学稿件或笔记，草稿也可以。如果项目文件夹或要处理的稿件还不明确，请问我它们在哪。如果我还没有稿件，请告诉我需要先提供一份数学稿件或笔记作为输入。保留原稿，另建游戏脚本，建好后直接开始自动化脚本验证。验证通过后，用通过验证的游戏脚本导出学习游戏。如果是我自己的未公开数学项目，也用同一份脚本生成完整稿件。如果是公开文献项目，同时生成一份针对原稿、面向作者的英文审稿报告。

引导期间，用户已提供的项目、稿件和类型直接复用。单独调用 `paper_ingest` 等模式时，按该模式的边界执行。游戏和稿件可并行生成，各自通过检查后分别交付。引导任务持续到全部适用交付物均已交付。阻塞仅影响某一项交付时，另一项继续推进。共享脚本存在实质数学问题时，按第 9.1 节暂停所有依赖该脚本的交付并恢复验证。交付游戏后是否分享、是否启动游玩，以及稿件是否公开，由用户决定。

## 3 项目类型、来源与持久保存

- 首次运行需要区分项目类型的功能时，由用户确认这是自己的未公开数学项目，还是以已公开数学文献为对象的项目。将类型保存在项目中，供后续运行沿用，包括自动化脚本验证、`writer`、Explorer 和 Fixer。
- 用户自己的未公开项目中，Explorer 按项目的研究目标探索证明，Fixer 按数学审查发现修复论证。
- 对于公开文献项目，Explorer 推进证明时、Fixer 修复论证时，都必须查阅目标原文中的相关论证，并沿其核心路线处理。原文确认有硬伤且修复必须偏离原路线时，按第 6.5 节处理。
- 处理公开文献 A 时，明确告知常规数学 Reviewer「不受文献 A 影响」。Reviewer 依据当前稿件的陈述、假设和推导独立判断数学正确性。与 A 的核心论证路线是否相符，由公开文献模式收尾时的独立审查员对照原文判断。
- 验证公开文献 A 的项目时，以本次处理的具体版本的公开日期为文献使用的截止点。参与项目验证的 AI 角色均不得以该日期之后公开的文献或其中的结果、证明方法、补充和勘误作为依据。供验证使用的检索结果、本地 `references/` 与角色输入均按该截止点筛选。游戏中的自由对话按第 8 节处理。

### 3.1 项目状态与恢复

- 每个数学项目保存原稿、游戏脚本源码、引用与书目信息、所需资源和编译配置，以及恢复审查所需的实际角色会话、结果绑定、分类、计数和暂停点。使用项目工作分支记录可恢复的研究检查点。新会话接续时复用可验证成果，仅重查失效或无法核验的范围。
- 项目工作目录尚未有 Git 仓库时，Proof2Game 自动在该目录建立本地仓库，用于保存可回退的检查点，随后继续运行。
- 项目将参考文献的原始 PDF 保存在 `references/`。自行编译的 PDF 用于核验与交付，长期保存可独立重建的源码与资源。失败要保住上一份有效稿件、结果与可恢复状态。旧 nonpass 不能自动升级，已完成工作不能重复计数。
- 恢复时核实真实会话及结果与受审版本的绑定。已保存会话 ID 不代表宿主可以恢复原会话。若无法恢复，先说明缺口，保留已验收结果，再按该角色的新会话边界安排替换。项目操作不授权推送、合并、对外分享或使用其他项目材料。

### 3.2 文献发现、版本与来源核验

- 查找依赖文献时，先检索当前项目的 `references/`，缺少所需文献或所需版本时再上网找。依赖文献优先使用符合条件的正式发表版，包括 online-first。发现本地只有预印本时，核实是否已有适用的发表版。用户明确指定依赖文献的预印本时，按实际选用的版本核验、记录并引用。
- 确认符合项目版本要求的发表版存在但拿不到对应 PDF 时，默认暂停相关步骤并请求用户提供。核实没有符合条件的发表版时，主动获取可合法访问的预印本。记录文献身份、实际版本、公开日期、核查日期、证据和结果。未发现符合条件的发表版的记录可复用，出现新线索或用户要求时重查。发表状态不明须如实记录。付费、新账号和访问限制按用户授权处理。
- 公开文献项目查找依赖文献时，先按各具体版本的公开日期筛选，再在截至项目截止日期已公开的版本中优先选正式发表版。如果符合日期要求的只有预印本，核实它包含所用结果后直接采用。核实版本、日期与原件的一致性。通过检索或模型记忆得到的后出简化、补充或勘误不得成为数学依据。来源摘要只能用于定位原文。
- 稿件的外部数学依据须可核实为公开材料，公开预印本和已公开但受订阅限制的论文均可。正式核验以实际 PDF 为依据，记录路径、版本、SHA-256、页码及结果定位。核对被调用结果的完整陈述、假设、适用范围及使用处的实例化。通常无需重审外部定理本身的证明。教材、专著、综述准确陈述所用结果时可以作为来源。
- 已正确核验并显式引用的稿内结果可复用。对不同对象、参数或条件重新应用外部定理时，要核验新应用。真正例行的背景工具可免逐项引用。自足证明确实不再调用启发来源时，可按实际归属处理。实际复用、改写、修复和接口优化均承担同样的核验责任。
- 核验当前证明或具体文献简化机会所需的来源拿不到时，暂停相关步骤并请用户提供 PDF。并行审查中，等待来源的 Reviewer 保存暂停点，其他能够完成的审查继续，已确认的问题归入本轮 Fixer 批次。用户尚未提供所需外部文献时停在 Fixer，保留已有审查结果和修复材料，待文献补齐再继续修复和后续阶段。串行步骤在当前步骤等待。取得并摄取原件后，从原暂停点自动恢复，保留当前轮、角色连续性与计数。
- 用户确认拿不到核验当前证明所必需的 PDF 后，等待该来源的 Reviewer 在来源核验关判 `nonpass`，指出缺少哪份文献及哪一步无法核验。待本轮审查结果全部收齐，由 Batcher 按第 6.2 节统一交接，Fixer 尝试补出可独立核查的自足证明。

### 3.3 参考文献保存与单独入库

- 每份入库参考文献按实际采用的版本，将原始 PDF 保存到项目的 `references/`。参考文献入库、审查续接和交付均无需逐页 OCR 或 Markdown 转录。来源审查直接阅读 PDF 的相关页面，按第 3.2 节核对版本和引用位置。
- `paper_ingest` 单独调用时，核对版本并保存指定文献的原始 PDF 后结束。已有同版原件可直接复用。引文不会触发自动批量入库。为审查补齐所需 PDF 后，从原暂停点恢复。

## 4 游戏脚本结构

### 4.1 两节结构与遍历

- 第一节直接为 **Main Results**，陈述主结果及必要约定。第二节为 **Detailed Proofs**，按主结果出现顺序组织证明树，逐棵深度优先展开。脚本省去 Introduction、Motivation、Perspectives 和独立的 Proof Architecture 节。
- `main.tex` 是组件、顺序和证明树的唯一结构权威。它显式输入 canonical components。组件恰分 convention、statement、proof。每个 theorem-like statement 与唯一 proof 配对，导航与论文内部引用都使用稳定标签。外部结果是 convention 中的接口，按第 4.3 节处理。
- 每个主结果在 Detailed Proofs 中对应一棵证明树，所有证明树按同一份 `main.tex` 的顺序装配。主结果的归约、所需约定、子证明义务和配对证明都落在相应节点。子结果先陈述，再由父节点的证明引用。共享引理及其配对证明只写一次，放在按稿件顺序最先使用它的证明分支中。之后的分支通过稳定标签引用已闭合的结果，并核对适用条件。
- 证明节点随层级嵌套，叶节点也有明确位置，深度不设任意上限。依赖已闭合且当前证明义务真正完成后，结果才供后续证明使用。没有子义务的结果也须实际闭合。引用方向冲突、循环、提前依赖须报告结构问题，不能通过动态跳过、重排或借用尚未闭合的结果掩盖。
- Statement 只陈述结果，Proof 判断是否完成配对义务。一个页面的结论或审查通过不能替代另一个页面的核验。约定可用与结果可用分别判断。

### 4.2 约定、作用域和导航

- Main Results 可设单一根约定、按实际数学背景排列的分块约定，或公共根约定加分块增量。按文档顺序累积并适用于其后陈述，禁止覆盖、遮蔽或追溯修改已陈述对象。显式引用先前结果，出现顺序本身不表示依赖。
- 每棵顶层证明树显式采用其主结果陈述位置的完整背景，包括已有公共根和适用的连续分块。子节点通过树继承精确背景。每节点至多一个完整的本地约定，放在直接输入之首，作用限于当前证明、随后声明的子义务与其后代。必要共享背景放在最早共同作用域。局部约定不能改变当前目标含义、增删义务或污染兄弟分支。WLOG 要在引入处说明合法性。
- Adoption 采用 “We adopt the settings ...”，使读者可直接定位真实层级与连续前缀。单一位置显示一次编号。父节点到子节点的继承从实际结构计算。

- Proof 是否需要结构分解由数学阶段、关键归约、中间结论和实际依赖是否清楚决定，不按字数、页数或段落阈值。
- 即使数学正确，单块写法掩盖真实独立阶段或主线也属 substantive exposition issue，须修复并 fresh 重审。
- 分解须抽取有数学意义的完整 statement、paired proof 与 proofnode。新子结果按首次使用处的直接依赖确定其在证明树中的位置。例如，C 直接用 B、B 再用 A，且两者都是新引入的结果，则 B 放在 C 下，A 放在 B 下。对已在前文闭合的结果，保留直接引用作为审查依赖。
- 新中间 statement 必须先于直接使用它的 proof；所有配对、context、依赖、universe 与 updater 要求继续有效。
- 每个普通 theorem-like statement 后、环境外，紧接 reader-visible 导航句，其语义为 “The proof of <Kind> <number> is given in <structural-level> <number>.”。
- 左端显示真实结果类型与自动编号，右端显示真实层级与自动编号；双方均不附描述性标题。深层名称随层级扩展为 Subsubsubsection 等，不统一退化成 Proof node。
- 导航只表示去哪里读 proof，不是数学结论或完成认证；缺失、错误、含糊、失效导航是表达关的实质问题。
- 导航和结构标签由唯一配对与稳定引用维护，不让 proof component 重复手写自动位置标签。
- Statement 描述性小标题可选，不强造；存在时 statement 标题与对应 proof heading 使用同一权威值，后者形如 “<title>: Proof of <Kind> <number>”，无标题则只显示 Proof of。
- 实际编译并核对 PDF 文本的编号、层级、空格与引用，不只检查 TeX 源码。一般 游戏脚本修改须编译 main.tex；不额外要求逐页人工式视觉验收所有 PDF。

### 4.3 外部数学接口和排版

- 本文必须自足说明实际使用对象、定义、方程、归一化、参数、假设、量词、范围与结论；“某文 equation (20)”或 citation 列表不能代替这些内容。
- 要求覆盖 statement 前后 prose 与正式环境，不能把缺失对象定义藏在环境外来规避。
- 接口只包含当前已识别消费者需要的最小完整规格，不为未来潜在用途复制来源 machinery。
- 引入来源特有对象须给本地可消费的存在性规格；若多个消费者需要同一个 witness，明确固定同一 witness，不能每次各取一个。
- 若唯一外部 formal content 是满足前述完整规格的 witness 存在，用 convention prose 的引用句即可，不强造 theorem-like 声明、编号或下游 ref。
- 作为独立结论调用的外部结果，放在 convention 内带唯一标签的 theorem-like declaration，消费者显式 ref；它是 convention 内容，不增加第四类 component，也不产生 paired proof。
- 来源须直接、明显支持本文声明。非平凡特化、桥接、拼接或额外推导回到本文普通 statement 与唯一 paired proof，不能藏在 convention、归属说明或 optional inline proof。
- 正常 provenance 放环境外简短标准说明，citation 不塞进 theorem optional title；必要归属与简述补充验证可保留，遵守第 5 节的文献复用规则。

#### 排版与书目

- Living 推荐模板为 `amsart`、12pt、显式 A4，左右各一英寸；纵向布局沿 amsart 与 calclayout。
- 参考文献用 inline `amsrefs`，在 hyperref 后加载，main.tex 末尾 bibdiv/biblist 与结构化 bib 条目；正文使用 cite。传统 BibTeX 与独立 references.bib 不再是要求。
- 每次新增数学参考文献都查 zbMATH，核对身份与书目信息；找到可靠匹配后保存非打印 Zbl 元数据，不让它进入最终 PDF 参考文献。
- zbMATH 未找到不证明文献不存在，也不阻止按出版社或 DOI 正式元数据引用；不能虚构 Zbl。元数据冲突先核验正式出版记录，仍无法解决才找用户。
- 游戏脚本结构和排版不能反向限制第 9 节生成稿件的组织自由；数学准确性、可核查性和准确书目信息仍须保留。

## 5 数学审查、范围和写入

### 5.1 初始化与分类

- 令 `M` 为 `main.tex` 的全部组件，`U = safe ∪ unsafe` 为当前审查范围，`M − U` 为范围外。Safe 表示当前无需再审，unsafe 表示需要审查，二者在 `U` 内互斥且穷尽。Safe 随具体版本、依赖与上下文变化。
- 引导模式新建脚本后，先将 Main Results 的全部组件纳入审查范围并登记为待审，保留已有可验证状态，直接进入自动化脚本验证。Detailed Proofs 的组件按第 6.3 节依据所有主结果的依赖并集纳入。引导模式交付须覆盖所有交付目标及其有效依赖。接续已有独立脚本且缺少有效审查状态时，先验证结构并核对可验证的既有审查记录。纳入范围的组件若没有有效审查记录，登记为 unsafe。
- 系统按纳入规则和第 7 节的更新条件设置 safe 与 unsafe。恢复沿用已有账本和有效状态。

### 5.2 范围身份

- 初始化后，Explorer 依据所有当前目标定理的实际依赖并集统一确定 `U`，按第 6.3 节纳入或移出组件。
- Universe 约束审查调度，不限制可靠修复所需的写入范围；Fixer 可修改范围外组件，但它们仍在范围外。
- 删除组件使其离开 `M` 与 `U`。仍存在的组件由 Explorer 按第 6.3 节依据当前依赖并集移出 `U`。移出 `U` 只清除当前 safe/unsafe 分类，源码和历史审查记录继续保留。
- 纯移动或改名且数学身份不变时，保留原组件身份及 universe 成员资格。若移动实质改变了某条陈述的阅读衔接，按第 7 节将受影响的陈述重新标为 unsafe，走现有复审流程。
- 拆分时若保留并修改原组件，它是唯一主继承者；其他新组件不自动纳入。若删除旧组件再创建新组件，旧成员退出，新组件均不自动继承。
- 合并按实际删除、创建、修改与移动逐项判断，不定义额外合并继承，也不按内容相似度事后猜测。

### 5.3 目标定理的修改

- 在用户已授权的工作范围内，Fixer、Explorer 和重构流程可自行调整辅助引理、约定及证明，保持目标定理的数学含义。
- 如果需要改变目标定理的数学含义，进入 `refactor`，向用户说明具体改法、理由及对结论的影响，得到明确确认后才实施。增加假设、削弱结论、删去目标定理，以及通过调整约定或定义间接改变其含义，都适用此规则。

### 5.4 递进关卡

| 页面类型 | 必须按序完成的原子义务 |
| --- | --- |
| Statement | 表达与可读性 → 正文自足性 → 数学正确性 → 外部来源核验 → 文献复用 |
| Convention | 开场定向 → 全文表达与可读性 → 正文自足性 → 数学正确性 → 外部来源核验 → 文献复用 |
| Proof | 表达与可读性 → 证明结构分解 → 正文自足性 → 数学正确性 → 外部来源核验 → 文献复用 |

- 已取消 Proof 的证明标准性分类关；不再要求 must_keep_full、clearly_standard、borderline、局部标准性证书、短证明认证或其依赖就绪调度。
- 每次只下发当前一项义务给该 component 本轮持续 Reviewer；通过才继续，首个 substantive issue 即 nonpass 并短路。修复后新轮 fresh Reviewer 从第一关重审，不沿用旧轮 pass。
- 本轮 Reviewer 会话无法恢复时，由一位新的 Reviewer 将该未审完的组件从第一关重新审查。其他组件已经完成且仍有效的审查结论继续保留。
- 各关只判断本职责内有无 substantive issue。影响理解、正确性、自足性或必要导航的缺陷可阻断；纯可选润色不阻断，不增加并列的 minor/major、blocking/non-blocking 等必填等级。
- Reviewer 不能跨关包办其他职责；只有全部原子义务通过才形成 component 最终 pass。

### 5.5 精确信息边界与读者连续性

- 外部来源核验之前的所有关卡必须 source-blind，包括 Convention opening 与 Proof decomposition；不得读取外部 PDF、sidecar、摘要或网络内容。数学正确性关把正文已自足写出的外部接口暂作前提，只检查内部使用合法性。
- 实际 payload 与可用上下文必须执行隔离，不能一面说不查来源、一面预先提供全文。后续来源信息不能倒灌以原谅前置问题或重写先前结论。
- 公开文献项目的常规 Reviewer 同样遵守关卡输入隔离。来源关只发核验外部接口所需材料，原文的路线、地位或既有结论不影响先前独立的稿内判断。
- Reviewer 获得当前页面、完整有效 ambient conventions、其职责所需的直接依赖 statement interfaces，以及 proof 的 paired statement；不无界展开更深依赖或其他页面的 proofs。
- Convention 开场判断只可获得当前 section-like 标题、规范 adoption、完整 inherited ambient conventions、显式引用的 prior statements 与有限 opening prefix；在判断前不读 prefix 后文、前一节技术性结尾、后续 components 或 referenced proofs。现行可保持的隔离粒度为首个非空段落；具体字段和协议不是用户界面。
- 开场须让首次顺序阅读者在新对象、observable、duality、construction 或主要工具出现时知道引入什么、为什么此刻引入、大致有何作用。若只能靠后文倒推，则 nonpass；不强制固定模板、section-goal 句或提前写出全部技术细节。
- Inherited conventions 是已知数学背景；已定义记号不必本页重述，作用已由背景与标题清楚表达也无需重复。继承内容自身的问题不在当前页重复追责，只审当前错误使用、冲突或非法实例化。
- 开场通过后，同一 Reviewer 才收到完整 convention，检查其余表达问题。全文关必须获得精确完整正文，不准以 opening excerpt 或只有路径元数据代替。
- Statement 表达关须看装配顺序中的紧邻前文与当前开头，必要时包括前一 component 和两次 input 间直接过渡 prose；不能只看孤立页面。关系已自然清楚无需套模板，若突兀转换对象或任务则须最小充分的数学过渡。
- 此窄幅衔接检查不扩张为对全篇 prose 的一般文风审查。
- 不准以未经解释的自造术语、workflow、component 或 ambient convention 来源等组织元语言替代数学表达；正常生成的 settings adoption 与 proof locator 是明确导航例外。
- 可要求原文证据、定位和简短可检查理由，不索取隐藏推理过程。独立盲测同时检验坏开场检出与好开场误报，不靠名人角色或单次结果声称稳定。

### 5.6 数学正确性与文献复用

- Convention 审查定义、记号、对象、变量、作用域、standing hypotheses、自洽性及与 ambient settings 相容性；不要求它证明 theorem。若把应独立证明的非平凡 claim 塞进 convention，报告职责与接口问题。
- Statement 审查 well-formedness、量词、域、假设、结论、参数、记号、依赖实例化与语境合法性，不要求本页推出结论，也不审 paired proof 的完整性或正确性。
- Proof 以 paired statement 为精确义务，核对覆盖、实际使用处依赖适用性、循环、隐藏假设、遗漏和边界情形、极限或积分交换、收敛与一致性变化和引用缺口；不能替目标重设计或暗改结论。
- 三类 verdict 独立，paired proof 通过或失败不直接覆盖 statement verdict。仅本节下文规定的 Statement 来源与复用有限核对是例外，不扩张到前置数学审查。
- 数学正确性关要求：非平凡义务必须明确闭合，不能因直觉、熟悉、可能为真或 Reviewer 自己会补证就放行。确实直接、唯一、无隐藏条件的机械短推导可省略；有实质疑问则要求足够论证。
- Fixer 对所有 findings 独立核验。数学修复须结合结构洞察与数学技术，可替换 Reviewer 的局部方案、寻找更干净证明；纯语言、排版、导航修复不套这一数学角色。
- 不模仿难读、跳步、过度压缩的文风，不借高能力做无关重写。角色不能只作装饰，也不能虚假自称名人或以名人身份代替证据。

- Reviewer 与 Fixer 即使尚未遇到错误或 blocker，也应在发现具体可能避免非平凡重复推导的文献机会时主动调查；不要求每个 proof 做穷尽文献检索。
- 单篇 literature opportunity 独立于数学 blocker、必要引用来源 blocker 与 refactor。提出机会不等于当前数学已经错误，不计为已完成 round、不运行 updater，也不改变累计审查计数。
- 正式判断必须核对可追溯的准确来源（包括直接读取的 PDF 原件），不能仅凭搜索摘要认定已有结果覆盖本文。
- 区分“来源具有实质相关性”与“当前稿件尚有实质复用问题”。只有后者要求文献复用关 nonpass；文献仍然相关，不意味着合理采用或澄清后问题仍未解决。
- 已正确调用来源、清楚交代已有结果与本文关系，并仅保留必要适用性验证或额外结论时，fresh Reviewer 可以独立确认通过，不得仅因重合再次拒绝。
- 仍认为存在可避免重复推导、缺失归属或未解决关系时，须指出当前稿件具体位置、尚未完成事项及证据。“文献覆盖该结论”本身不够。
- 在公开文献项目中，发现其他文献覆盖目标原文的部分论证时，仍可保留原文的推导。仅凭这种覆盖关系，文献复用关不得判为 nonpass、要求以外部文献的推导替换或将其记为路线错误。若另有实际的错误引用、缺失归属或数学缺陷，按相应关卡指出具体问题与依据。
- 正常学术归属、说明采用已有定理及简述本文补充验证可以保留。非平凡对应论证进入 paired proof；不得一关要求删去正常归属，另一关又以缺失同一归属为问题。
- Statement 的来源与复用两关可以有限核对现有 paired proof 是否已承担特化和适用性验证；不替代独立 Proof 审查，不准用 proof 补救 statement 本身不自足，也不回溯改变前三关。
- Fixer 独立核验 Reviewer 的诊断、建议与重写。判断为误报时，可在保持数学含义的前提下澄清容易误读的措辞，例如明确指出已适用的约定或假设。稿件已充分清楚时可保留原文。当前 nonpass 仍按更新规则处理，由下一轮 fresh Reviewer 根据届时稿件独立判断。
- 不以强制改写、重复润色或无人负责的循环来求通过。
- 可选复用机会所需的 PDF 无法取得时，即使当前稿件已有完整证明，也先暂停相关步骤并请用户提供。用户确认拿不到 PDF，或明确放弃该复用机会后，记录该来源未取得，跳过这次复用，自动继续审查不依赖该文献的现有证明。原路线若实际依赖该来源，则按第 3.2 节的必需来源规则处理。
- 同一任务的后续审查轮次复用已有的「未取得」记录。该文献仍为可选来源时，直接跳过复用并继续审查。若当前证明实际依赖该文献，按第 3.2 节的必需来源规则处理。

## 6 角色、工作流与停止条件

### 6.1 角色配置与独立性

所有下列模型和推理档位都是可按角色覆盖的默认值。实际运行时核对已配置角色的能力和真实会话身份，无法使用所选配置时说明缺口，不静默降档。自动验证由实际主持任务的 Codex 主会话负责，不能声称已切换正在运行的会话模型。

| 角色 | 默认模型与推理档位 | 职责与会话边界 |
| --- | --- | --- |
| 自动验证主协调员 | `gpt-6.2-sol / medium` | 持有同一 Codex Goal，实际协调调度、结果、恢复与决策 |
| 常规 Reviewer | `gpt-6-luna / high` | 每轮每组件使用新会话，当前轮逐关复用，同轮不同组件独立，最多十个并行 |
| Batcher | `gpt-6-luna / high` | 每轮新会话，无损汇总问题并交接 |
| Fixer | `gpt-6.2-sol / high` | 每轮新会话，串行处理本轮全部修复批次 |
| Explorer 与 Interface Optimizer | `gpt-6.2-astra / high` | 每次 Explorer 新会话，同次后续接口优化沿用该会话 |
| 未公开项目的证明简化审查员 | `gpt-6.2-sol / ultra` | 每次路线评估独立，比较完成后的实际证明 |
| 公开文献项目的独立路线审查员 | `gpt-6.2-sol / ultra` | 对照目标版本，每次复审使用新会话 |
| Refactor 实施代理 | `gpt-6.2-astra / high` | 确定方案后新会话实施 |
| Writer | `gpt-6.2-sol / ultra` | 负责完整成稿与自查 |
| 游戏制作代理 | `gpt-6.2-sol / medium` | 从已核验的快照制作和检查双语游戏网站 |
| 游戏翻译代理 | `gpt-6.2-sol / medium` | 翻译完整快照，核对数学忠实性 |
| 游戏内导师 | `gpt-6.1-terra / medium` | 用玩家所选语言在本机游戏中响应 |

协调员可用脚本辅助调度及机械检查，自行核对、接受、绑定和推进结果。Reviewer 只收到当前关卡需要的材料。先前的审查意见、Fixer 对误报的判断及其理由、预期结论和尚未允许的来源均留在审查上下文之外。不同组件独立推进各自关卡，平台可用并发较少时按实际能力调度。

### 6.2 自动化脚本验证的内部审查

单轮审查 `proofreader` 和连续审查 `proofreader_loop` 仅由自动化脚本验证调度。

#### 单轮审查 `proofreader`

- 本轮从连续审查接收送审清单。清单为空时直接返回。对每个送审组件启用一位 fresh Reviewer，逐关审查，首个 nonpass 即结束该组件本轮审查。通过全部关卡才产生最终 pass。
- 等本轮所有送审组件都取得审查结论后，Batcher 才将 Reviewer 提出的所有问题无损交给同一个 Fixer，Fixer 随后开工。有 Reviewer 按第 3.2 节等待文献时，其余 Reviewer 可继续审查，已经返回的问题留待本轮结果收齐后统一交接。Fixer 串行处理全部修复批次，依据前序修复后的稿件逐项判断。若某项已被前序修改解决，或已随证明路线变化而不再相关，记录理由并继续。对仍成立的问题，Fixer 自主决定如何修复。
- 原 Fixer 会话无法恢复时，由一位新的 Fixer 接收本轮完整问题清单、暂存稿件和已有处理记录。新 Fixer 核对已完成的修复，保留仍有效的修改，再处理剩余问题。
- 后续修复如需重新使用先前废弃的组件，Fixer 可将其恢复到证明路线中。审查范围由 Explorer 根据修复后的依赖重新核对。本轮所有问题都应有处理结论。
- Reviewer 负责指出具体错误或疑点及证据，不强制给出可靠修复。Fixer 独立诊断并尝试修复，只有它判断无法可靠完成数学修复时才成为 mathematical blocker，自动进入 refactor。
- 修复不限于原审查目标，可必要地修改 dependencies、consumers、conventions、statements、proofs 与 main.tex；可创建、拆分、合并、移动、重排，但不能用空白占位延后同一数学缺口。
- Fixer 按第 5.3 节自行调整辅助引理。修复涉及目标定理的数学含义时进入 `refactor`。
- 纯可读性问题无法可靠修复或被 Fixer 认定误报时，当前 nonpass 仍使组件 unsafe，留下一轮 fresh review；不因此强迫数学路线 refactor。
- 修复完成后按 Proofreader Updater 分类并结束本轮，由连续审查决定是否开启下一轮。
- 本轮中途进入 refactor，把本轮已有 Fixer 修改和确认后的 refactor 修改作为同一完整修改集合，仅执行一次 Proofreader Updater，不另用 Refactor Updater。
- 停止报告包括本轮发现、可靠修复与未解决问题、实际修改的组件、完整 safe/unsafe 列表。每轮在对话报告。公开文献原文的硬伤另按第 6.5 节记录在项目报告中。

#### 连续审查 `proofreader_loop`

- 令 `C` 为当前所有主结果的完整依赖并集。每轮开始前按当前脚本计算 `C`，只将 `C ∩ unsafe` 送审。轮内沿用常规审查、修复与更新器规则。
- 每轮应用修改并完成 updater 后，按更新后的脚本重新计算 `C`。`C ∩ unsafe` 为空时完成本次 loop。起点交集已为空时直接完成，不运行空轮。交集非空时自动开始下一轮。并集外仍标为 unsafe 的组件不阻塞 loop，范围的增删交给 Explorer。
- 连续审查按当前送审范围决定何时完成，无固定轮数上限。
- 只有完整执行 updater 后才计为已完成 round；中途暂停不提前计数。恢复保留累计轮数、修改、分类和暂停点，不重新初始化或重复计数。
- Refactor 修改并回原 round，只执行一次 Proofreader Updater；该 round 完成后正常计数并按结果续跑。
- 来源等待、refactor 决策、真实能力缺口及明确用户暂停等既有暂停边界继续有效；不得仅因达到某个轮数而暂停或请求续额。
- 停止报告包括原因、已完成轮数、主要修改和完整 safe/unsafe 列表。

### 6.3 主结果依赖并集与接口优化

Explorer 仅由自动化脚本验证调度。

- 第一批审 Main Results 的全部组件。随后每次 Explorer 从 Main Results 中的所有主结果出发，沿实际依赖追溯到底，一次处理这些结果及其完整依赖的并集。并集包含各层级所需的约定、陈述与证明，共享组件只纳入一次，各组件独立审查。
- 当前依赖并集 `C` 与 unsafe 的交集为空后，Explorer 根据当前脚本核对并集，把已离开该并集的组件移出 `U`，并把仍在并集内且尚未纳入的现有组件一次性加入 `U`。Explorer 不为送审新建组件。游戏脚本的深度优先排版顺序仍由第 4 节规定。
- 每次探索时，仅对原先在 `U` 外、拟纳入的组件检查接口是否过强。对有机会实质降低证明负担的陈述尝试弱化。根据实际应用优化后的当前脚本确定最终纳入与剔除清单。新纳入及重新纳入的组件进入 unsafe，仍在范围内且有效的审查结果继续有效。

- Explorer 在同一会话里自动尝试弱化过强的接口。有效弱化须仍支持全部当前直接使用处，且实质减轻证明难度或删除非平凡证明义务。若多项弱化影响同一份证明，按合并后的候选核对该证明。可行的优化应用后与本次新纳入的其他组件一并送审；找不到有效方案的组件按原样与本次新纳入的其他组件一并送审，单凭弱化失败不触发 refactor。
- 公开文献项目中，Explorer 应对照本次处理的原文版本，只采用保留核心论证路线的弱化方案。弱化后，关键归约、估计或构造等论证仍须可追溯到原文。若某项弱化会省去或替换关键论证，按原陈述纳入审查。
- 附加说明。Explorer 在追踪依赖或尝试弱化时，若碰巧发现拟纳入的组件可能有错误或缺口，可顺手尝试修正一次。修正须遵守第 5.3 节的目标定理规则和公开文献核心路线的约束。能可靠修正就把修改后的组件随本批送审，否则按原样送审。新纳入的组件均进入 unsafe，由常规流程审查。
- Explorer 实施接口优化或顺手修正后，只执行 Interface Optimizer Updater，随后由自动化脚本验证按第 6.4 节继续调度。

- 交付快照只保留交付目标及其依赖。Explorer 判定已脱离交付目标依赖而移出的组件视为废弃。游戏与 `writer` 直接将其视为不存在，废弃组件不参与交付验收、翻译、关卡生成、导师上下文或稿件写作。只被废弃组件引用的资料也不进入交付。交付快照按保留内容核对结构、编号和引用。工作稿中保存的废弃源码与历史不变。

### 6.4 自动化脚本验证的共同流程

- 启动引导模式或单独启动自动化脚本验证时，主 agent 根据当前项目、用户已授权范围和实际保存状态，通过 Codex Goal 建立持续追踪的目标。目标按入口写明任务范围与完成条件。
- 引导模式沿用同一个 Goal，直至所有适用交付物均已实际生成并通过各自检查。单独启动自动化脚本验证时，同一版脚本完成数学审查、闭合全部证明义务并通过第 6.5 节收尾审查后，标记 Goal 完成。
- 恢复任务时先检查已有 Goal，复用对应的未完成目标并保留其他目标。以项目中记录的同版审查、证明闭合和适用的交付检查结果为完成依据。Goal 生命周期遵守宿主实际工具规则。缺少 Goal 能力时如实报告。
- 当前 `C ∩ unsafe` 非空时先运行 `proofreader_loop`，为空时直接运行 Explorer，不运行空 loop 或增加已完成 loop 次数。
- Loop 清空 `C ∩ unsafe` 后运行 Explorer。Explorer 按当前依赖并集调整范围及尝试弱化。完成后按更新后的 `C ∩ unsafe` 决定是否启动下一次 loop。
- 不设内层 Proofreader round、外层 proofreader_loop 调用或 Explorer 步数上限。取消原七轮/七次限制、配额边界暂停以及委托助手或用户的全部续额流程；无需通过周期性续额审查才能继续。
- 一次外层 loop 调用直到当前 `C ∩ unsafe` 为空才完成。中途来源等待、refactor 或其他暂停不另起调用，也不重复计数。持续保留累计轮数、loop 次数、Explorer 进度与当前状态。
- 内部 Proofreader round 进入 refactor，修改并回该 round，只执行一次 Proofreader Updater，并在同一次 loop 继续。
- Explorer 或 Optimizer 阶段进入 refactor 时，没有进行中的 Proofreader round。确认修改仅用 Refactor Updater，随后按当前 `C ∩ unsafe` 决定开始新 loop 或继续 Explorer。
- Optimizer 成功修改仅用 Optimizer Updater，后续按当前 `C ∩ unsafe` 衔接，同一次修改只运行对应的 updater。
- 进入收尾路线审查前，须确认当前依赖并集 `C` 中的全部组件都已纳入审查范围且为 safe，并且目标的证明义务已全部闭合。若尚不能确认闭合，应查明并说明原因，按既有推进或暂停规则处理。refactor 决策、来源等待、真实能力缺口和明确用户暂停等既有暂停点继续有效。
- 自动化脚本验证的主协调员 自己负责持续运行、判断实际进展与决定是否遇到需要用户处理的暂停点；不依赖另一个监督 agent，也不由委托助手周期性审查或批准继续。此项保留各数学 workers 的独立审查职责，不把这些职责合并到主 agent。
- 若主 agent 有具体证据确认同一问题或修改反复出现、缺乏实质进展，且无法自主解决、需要用户决策，则暂停并给出证据，与用户讨论。无需固定检查周期，不仅因轮数多、证明困难或一般不确定性而停；不能仅凭计数或哈希判断反复。
- 取消次数上限不授权绕过真实数学 blocker 或用户决策；其他无法解决且需要用户决定的问题仍应给出具体证据并进入既有讨论流程。
- 停止报告包括原因、外层 loop 次数、主要数学修改、完整 safe/unsafe 列表及最后一次 Explorer 结果。

### 6.5 两类项目的收尾审查与内部 `autorefactor`

两类项目均在满足第 6.4 节的证明闭合与依赖审查条件后进入收尾审查，且须通过同版审查后才能完成自动化脚本验证。引导模式后续交付需要所有交付目标及其依赖满足条件。内部 `autorefactor` 由同一主会话协调并沿用同一 Goal。每次动手前在当前项目的工作分支保存明确、可回退的 Git 检查点，保留修改与失败记录。方案按本节自动实施，目标定理的修改按第 5.3 节处理。

**用户自己的未公开项目**

- 证明简化审查员读取当前完整游戏脚本和历次尝试，判断是否有可实施的实质性路线简化。缩短文字、调整排版或纯叙述重组不构成证明简化。
- 证明简化审查员可以参考工作稿中保留的废弃分支。若重新使用其中的组件可以简化当前证明，允许将其纳入候选路线。实施后由 Explorer 按新路线重新计算依赖并集，重新纳入的组件标为 unsafe，走现有审查流程。

- Autorefactor 可以为简化证明改变路线，包括调查并核验可替代原有论证的外部定理。新路线须数学正确，完成后按下文比较取舍。此权限属于自动化脚本验证内部研究阶段，后续 `writer` 按已验证脚本写作。文献核验及后续独立审校义务继续适用。
- 若存在该类简化，主会话按简化审查员的方案自动启动 refactor、修复及相应 updater，然后自动重新进入 自动化脚本验证；该来源的路线方案不再要求用户逐项讨论批准。仍按既有 updater 及 fresh 审校规则处理修改，不能把方案、修复或 updater 本身冒充重新通过数学审查。
- 若实施或后续审校确认简化方案确实不可行，git 回退到该次 autorefactor 前的检查点，再启动一个新的 autorefactor 会话重新评估，而不是直接停下来要求用户决定路线。新会话须知道前任尝试的方案、实际失败位置与原因，不能把已证实的失败当成未尝试路线重复提出。回退恢复检查点对应的稿件及有效研究状态，但须保留失败证据与实际发生的尝试、审校和累计记录，不因回退抹去历史。一般可修复的审校问题仍按正常修复流程处理，不把一次 nonpass 自动当作方案不可行。
- 简化方案的初步判断不等于最终简化成功。新路线完成实施及后续自动化脚本验证审校后，须结合实际完整证明与原检查点路线比较；若此时发现原路线反而更简单，即使新路线数学上正确、能够完成，也算“简化失败”，允许回退到原检查点，再由新的 autorefactor 重新评估。不得仅因方案已经实施或证明已通过就保留较复杂的新路线。
- 两条路线均正确且各有取舍，无法明确判断哪条整体更简单时，由主 agent 自主决定保留新路线还是回退，并记录取舍理由。
- 跨 autorefactor 会话保留路线尝试及比较记录，覆盖数学不可行与完成后未实现简化两类失败；记录原路线、候选路线、实际实施/审校结果、最终复杂性比较及回退原因，并在后续评估时提供。回退不得删除这些记录；后继评估须据此避免在已比较的路线之间反复横跳，不能遗忘已完成的尝试而再次把同一逆向切换当作未经检验的简化。
- 重启自动化脚本验证后继续通常的审校与探索；再次达到原停止条件时，重新进入 autorefactor 检查。未发现可实施的路线级简化时，才到达正常结束点。既有 universe、来源、真实能力及用户暂停边界不因本条自动取消。

**已公开的数学文献**

- 数学审查通过后，由独立路线审查员对照本次处理的公开版本，确认关键论证可追溯到原文，核心路线相符。允许补齐省略步骤、调整顺序和等价表述，不要求逐步一一对应。
- Fixer 对照目标版本确认原文核心论证有实质错误或缺口时，维护一份项目内报告（`report.md`）。记录原文版本及页码、公式或段落定位，具体错误及可核查依据，受影响的结论和修复结果。若必须绕开原路线，记录偏离的位置、必要性与替代证明。
- 必要绕道按常规流程接受独立数学审查。收尾路线审查员读取同版脚本与报告，核验原文硬伤及绕道的必要性，确认后允许该处偏离，并继续核对其余核心论证。
- Fixer 无法可靠修复核心错误时，在报告中记录已查明的问题、影响及修复为何不可行，暂停自动验证并进入 `refactor`。若发现反例，Fixer 在 `refactor` 中直接向用户出示反例及具体依据，说明它如何满足原定理的假设、推翻哪一条结论，由用户决定是否撤回。此决策以 Fixer 的核验和呈示为依据，无需额外安排 Reviewer。
- 原目标定理有反例时，若用户在 `refactor` 中依第 5.3 节确认修订后的定理，记录原结论、反例及获确认的新结论，以新结论为目标恢复验证。受影响的组件重新接受数学审查，收尾路线审查员结合报告核对目标变更及由此产生的必要路线调整。通过同版审查后，按修订后的定理导出游戏并生成审稿报告，在报告中记录原文硬伤和经确认的结论修订。
- 用户确认撤回最后一个目标定理时，记录撤回决定与已核验的反例，引导模式直接衔接第 9.4 节的报告交付。
- 其他文献覆盖目标原文部分论证的事实本身不构成路线偏离。是否建议引用该文献，按第 5.6 节的文献归属规则判断。
- 未通过时进入 `autorefactor`，按审查指出的实际偏离恢复原文核心路线。若新路线无法实施，恢复该次检查点并记录原因及可核对证据，后续方案应参考失败历史。
- 修订后先让受影响内容重新通过数学审查，再由一位新的独立路线审查员复审同一版脚本。两项都通过才停止。独立审查再次失败就继续 `autorefactor`。后一版本须重新取得适用的审查结果。

### 6.6 手动重构与阻塞协商

- Refactor 是跨模式的双向讨论与采访，处理数学路线、来源等确需用户决定的 blocker；先说明具体问题、触发原因和证据。
- 主 agent 与用户共同讨论，一次只问一题；收到回答先对齐理解，用户纠正时撤回旧理解。有根据地反对错误、不可行或高风险方向，不一味迎合。
- 不固定提供 2–4 条路线、不设问题数或轮数上限，不让 worker 代替主 agent 与用户协商。
- 讨论中可读稿件和项目来源、做草稿推导或验证数学想法，但不能修改 正式游戏脚本。
- 共识形成后总结实际共同结论。涉及目标定理含义变动时，依第 5.3 节取得明确确认。
- 决定明确后在同一次流程立即执行商定行动。稿件修改由 fresh implementation worker 完成；只需摄取来源则摄取后恢复原流程；共识为暂不行动则保留可恢复暂停。
- 实施中发现方案不可行、需改变目标定理或出现其他实质决策点，回到同一次讨论，不作未确认的部分修改。
- 有进行中的 Proofreader round 时并回原 round，仅用 Proofreader Updater；否则稿件修改仅用 Refactor Updater。Standalone refactor 完成后停止，不自启 Proofreader 或 Explorer。
- 用户明确放弃未完成的自动化脚本验证或审查任务 并要求 standalone refactor 时，可在无活动写入事务的安全边界转换，不伪造旧结果或手改状态；保留分类与累计次数。
- 只有用户明确表示原先已确认的 no-action refactor pause 被取代或放弃，才可退出该暂停；退出须无活动事务、保留原共识回执，不改稿件、分类或累计次数，回到可启动已授权新动作的稳定边界。

## 7 分类更新器

每次已实施的修改只运行来源流程对应的更新器。分类基于具体的数学语义判断及理由，hash 用于绑定版本和检查字节一致性。

三类更新器共同适用阅读衔接检查。若移动实质改变了陈述与紧邻前文或过渡文字的衔接，将既有审查范围内受影响的陈述标为 unsafe，按常规流程重新审查。检查同时覆盖被移动的陈述和因移动而改变阅读衔接的其他陈述。

在隔离位置准备候选修改，记录对应的组件身份、起始版本、各项修改的数学目的及其对依赖、约定与配对陈述的影响。只有目标仍对应候选所绑定的版本时才能应用。应用失败要保留可恢复状态，重试不重复应用修改或累加计数。结构性改动须核对配对、引用、上下文及实际编译结果。

### 7.1 Proofreader Updater

完整 round 结束后，一个当前 universe 内的组件为 safe，须同时满足本节的阅读衔接规则和以下五条条件：

1. 若它在本轮起点为 unsafe，则其完整递进审查最终无 substantive issue；任一关 nonpass 均不满足。
2. 组件自身在本轮无 substantive edit。
3. 它直接依赖的 statement interfaces 在本轮无 substantive change。
4. 它的 ambient convention stack 在本轮无 substantive change。
5. 若它是 proof，其 paired-statement interface 在本轮无 substantive change。

Unsafe 是同一既有 universe 内未满足本节条件或因阅读衔接变化而需复审的组件。已删除组件退出。Fixer 已修复本轮 nonpass 也不能使第 1 条自动成立，须下一轮 fresh review。

### 7.2 Refactor Updater

仅当没有进行中的 Proofreader round 时使用。一个既有组件保持 safe，须同时满足本节的阅读衔接规则和以下条件：

1. 实施前已为 safe。
2. 自身数学内容或责任无 substantive change。
3. 直接依赖的 statement interfaces 无 substantive change。
4. Ambient convention stack 无 substantive change。
5. 若为 proof，paired-statement interface 无 substantive change。

只在原 universe 内保留仍有效的 safe，不使用新 review verdict、不把原 unsafe 升为 safe；新组件和范围外受影响组件仍在范围外，删除者退出。

### 7.3 Interface Optimizer Updater

Explorer 实施接口优化或顺手修正后，一个既有组件保持 safe，须同时满足本节的阅读衔接规则和以下条件：

1. 优化前已为 safe。
2. 自身数学内容或责任无 substantive change。
3. 直接依赖的 statement interfaces 无 substantive change。
4. Ambient convention stack 无 substantive change。
5. 若为 proof，paired-statement interface 无 substantive change。

更新器将既有审查范围内因本次修改而失效的组件重新标为 unsafe。原 unsafe 不能升级。Explorer 按第 6.3 节一次性纳入所有主结果依赖并集中尚未纳入的全部组件。实际实施修改时才运行 updater，同一次修改仅使用对应的 updater。

### 7.4 保义措辞修改

- Convention、statement、proof 的修复是否 substantive，由 Fixer 独立判断并给可核对理由，不能仅凭文字或 hash 变化决定。
- 有理由的保义修改不要求组件原本 safe、先通过数学关或另一个 Reviewer 在写入前批准。
- 保义说明不是数学正确性认证。实际改变数学内容须如实声明，并按相应 updater 处理影响；不能借 cosmetic 标签规避。
- 本轮 nonpass 的本人仍 unsafe，下一轮从第一关重审；纯措辞修复不额外失效数学内容未变的消费者或扩张审查范围。

## 8 `game_developer` 与玩家体验

### 8.1 生成与分发边界

- 引导模式在同一版脚本完成数学审查、闭合全部证明义务并通过该项目类型的收尾路线审查后，自动调度 `game_developer`。游戏导出只读核对交付快照与同版验证记录，从该快照生成可部署的游戏网站。游戏导出可与适用的 `writer` 交付并行，两者使用同一份已验证快照。
- 游戏网站以 Proof2Game 为系统名，保留引用文献的准确归属。公开文献游戏首页（连接页）显示原论文标题、作者和实际处理的版本。未公开项目省略作品标题及作者署名。
- 每份网站绑定固定的原稿版本和已验证的脚本快照，包含双语游戏内容、界面和面向玩家的启动说明。原论文发布新版本时，已发布游戏及玩家存档保持原样。作者明确要求把新版论文做成游戏时，按第 2 节另行处理，独立导出和发布。
- 核验后将可部署的网站交付作者。作者决定是否和何时部署及分享链接，未公开项目须经作者授权后才可公开部署。玩家通过第 8.10 节的网页流程启动。
- 游戏打开至英文地图。玩家玩法按下列规则运行。生成者的流程在交付处结束，作者可另行要求启动游玩。

### 8.2 树形地图与关卡

- 游戏从游戏脚本的第一个 canonical component 开始。
- HTML 地图直接依据稿件已有 section、component 与证明分解组织一棵或多棵树；statement 与 proof 分别设关，不另手工维护教学依赖树或擅自改排数学结构。地图画布支持上下左右拖动和滚动；拖动卡片不得误触进入关卡。
- Convention 也独立设关，与其所属 section 绑定，位于对应 section 节点及分支下方的入口位置；Main Results 的入口约定位于全树底部。保留稿件已有的 convention 组织，以 canonical convention component 为关卡单位，不跨作用域合并，也不自行重写为另一套专题课程。外部定理仍是 convention 中的数学接口，不凭空增加外部定理的配对证明关。
- 关卡的开放顺序遵循稿件 component 的实际出现顺序，包含 convention，不把 statement 与 proof 强制排成相邻关。初始仅开放首关，每通关一个新关卡开放下一关。
- 地图随进度生长。未来关卡默认隐藏；已显示 statement 的配对 proof 可上锁显示，section 的 convention 入口及其所引出的节点可按同一结构预览。可见不等于可进入，不绕过顺序开放。
- 已通关关卡可重新进入，保留此前对话并允许追问。全部 convention、statement、proof 关通过即全稿通关，不设综合考试或其他额外关卡。
- Statement / proof 地图卡片第一层显示类型与编号，第二层显示已有的具体标题。Convention 关统一称为 **Convention** 或 **约定**，地图卡片、关卡页面标题和引导中的称呼一致。稿件中的名称、作用域及关卡结构保持原义。保留清晰的开放、已理解、未开放状态。

### 8.3 关卡页面、数学显示与引用

- 进入关卡后直接铺满页面，不用带外圈留白、阴影和遮罩的悬浮卡片。桌面默认左侧数学内容约占 38.2%，右侧对话约占 61.8%；窄屏可适配排列。保留返回地图和导航能力。
- 左侧按所选语言直接显示对应 component 的英文原文或中文译文。不用目标概述代替正文，不另加背景折叠栏。标题上方不重复显示关卡类型和章节号等元信息。
- 公式、文本强调及二者混排均须正确渲染，不向玩家暴露原始 TeX/Markdown 标记；内容与引用不能因简化界面而丢失。
- 内部定理、公式和 section 引用可点击，在同一 HTML 页面体系中跳转到被引项所在的实际完整关卡页，并定位被引内容；左上角提供前进、后退。使用稳定编号和引用，statement 与已有公式保留稿件编号；无编号公式应有可区分的编号。编号不必作为卡片上的冗余标签。
- 引用导航同样遵守关卡解锁状态，包括指向后文的非数学推理导航（如 statement 到配对 proof 的位置链接）；目标关卡尚未解锁时显示 Locked（未解锁），不能打开，不因引用而提前开放。
- 证明页标题中仅被引的名称和编号（如 Lemma 3.1）是超链接，Proof of 与描述性标题保持普通文字。
- 外部引用按第 8.10 节链接到 DOI 或官方出处，保留作者归属及已核验的定位。
- 普通讲解只谈数学，不向玩家提及 游戏脚本、内部脚本或技能等制作机制；真实数学出处仍应保留，玩家明确询问来源或制作方式时如实回答。

### 8.4 全局语言与翻译

- Game developer 在导出阶段将已通过验证的英文交付快照交给一位精通数学和中英文的 agent 生成完整中文译文。译者先理解快照，再结合上下文自主处理译法，无需逐处向用户核对。难以准确翻译的术语可保留英文。左侧译文忠实保留英文快照的内容、结构、数学公式、编号和引用。补充讲解由对话承担。
- 游戏制作阶段核对译文忠实性和游戏导出质量。中文译文自身的错误在导出阶段修正并复查。若制作时碰巧发现英文脚本存在实质数学问题，按第 9.1 节交回复审。
- 首次直接打开英文地图。玩家可在地图或关卡随时切换，整个游戏使用同一种语言，包括界面、左侧稿件，以及 Guide 和 Regular chat 的新回复。进度、理解确认和已有对话保留，历史消息按原语言显示。下次打开使用上次选择。两种对话都能查阅英文原文，用玩家所选语言回答。
- 切换语言时若有回复正在生成，沿用同一条玩家消息，以新选语言回复。载入手动存档或导入进度时，保留玩家当前选择的界面与对话语言。
- 外部参考文献按分发方式使用相应的引用链接，右侧可以用所选语言讨论。双语要求用于今后新生成的游戏。

### 8.5 对话模式与引导目的

- 聊天输入框支持 macOS 汉语拼音输入法。按回车确认输入法组合中的候选词或保留所键入的字母时，只将文字留在输入框。组合结束后再次按回车才发送。

- 给 guide 一个明确目标：帮助玩家理解当前关卡，并由玩家明确确认理解、完成本关。运行时只提供为此必需的少量明确规则，其余教学判断交给 agent 在互动中自由发挥。不要加入“讲清主线与关键非平凡步骤、按需展开常规计算”等模糊的默认深度标准，不预定每行公式的覆盖或确认要求；讲什么、讲多深及怎样调整均依据实际互动。访谈中的具体情境用于解释已确认边界，不逐例扩充为教学算法或机械分支流程。
- 对话区上方提供 Step by step guide 和 Regular chat。新关卡默认 Step by step guide，玩家可主动切换至 Regular chat。每个关卡独立记住最后选择/互动的模式，重访、刷新、重启后恢复，不能把上一关的选择带入新关卡。切换模式不算确认理解；保留已确认范围及对话上下文，不恢复已作废的引导草稿为待完成目标。
- Regular chat 由玩家决定话题，只回应玩家的问题与请求，不主动开展或推进逐步课程，不显示步骤理解确认；思考等待提示使用 Thinking… 等符合普通聊天的说法。 可以跨关卡讨论整份稿件，当前关卡只是默认上下文；讨论其他关卡的内容不自动算作理解确认、通关或解锁。
- 公开文献项目的游戏中，玩家在 Regular chat 主动问到晚于项目截止日期的论文时，导师可以讨论，并明确注明这是目标原文公开后的进展。
- 每个关卡的 guide 开始时，先有自然、礼貌的开场白，简短带玩家进入交流并介绍这一关要一起理解什么，再开始第一小步；不要一上来就抛出一段要求玩家确认理解的内容。开场由 agent 按当前关卡和上下文自然组织，不固定套话，也不增加欢迎入口页或额外开场确认流程。
- Guide 类似有教学大纲的课堂：当前关卡所必需的理解内容是要完成的教学目标，agent 应主动掌握方向与节奏，根据反馈调整教法。玩家问超纲问题时，可以简短回应，但不能失去对当前课堂的引导或被带入无止境的旁支。教学内容目标与讲解草稿不同：必要内容仍应覆盖，具体路线和讲法可重新设计，不增加固定的逐层确认脚本。若玩家明确希望深入超纲旁支，guide 可以建议切换至 Regular chat，但不能自动切换；是否切换由玩家决定，未切换时 guide 仍围绕当前关卡教学目标推进。
- 每一个 guide 都应努力把玩家引导到完成当前关卡：持续围绕本关实际的理解目的，结合玩家反映自主选择有助于完成本关的下一小步。追问和讨论是调整引导策略的依据，可以改变切入点与路径；不以完整回答玩家所有问题为义务，也不无限偏离为天马行空的讨论。回到的是当前关卡的理解目的，不是追回已作废的草稿、父步骤确认或要求玩家赞同原文。完整关卡仍由玩家确认，Regular chat 不承担主动推进关卡的任务。
- Step by step guide 的每次回应都是一次尝试帮助玩家向前理解一小点的讲解。小步指认知跨度适当，不是固定句数、符号数或必须逐层完成的课程流程；默认不要捆绑多个新目标，也不要用高密度总结伪装成小步。不论玩家提问、评价还是给出其他反映，agent 都先重新判断怎样引导更有助于完成本关，再根据当下对话组织一小步讲解，并邀请玩家确认这一步是否清楚、有没有问题。不采用“先完整回答问题，再额外附加下一步”的固定模式；复杂问题尤其不追求一条回复答完，也不把每个问题列为必须逐项回答的任务。这一步由 agent 自行组织，不要求摘录 manuscript 原文。跨关卡问题也作为策略调整的输入，由 agent 判断何种简短回应和引导有助于当前关卡，不要求展开全部问题；讨论不自动通关或解锁其他关卡。
- 教学方法、切入点、例子、篇幅与步长由 Guide 按内容和互动自主选择。讲解具体对象时写清所用的定义。讲推理时尽量给出实际的等式或明确的数学关系，让玩家看见各量如何相连。可以定义稿件以外的临时记号，例如用等式给出右边第一项 (A)，在当前推理里使用，推完回到稿件记号。无需每步重抄整条长公式，也不设固定讲解顺序或公式数量。此条是 Guide 的讲解要求，Regular chat 的回复形式随玩家话题决定。
- Guide 认为图片有助于讲清当前这一步时，可以自行生成图片，并直接嵌入这一步的对话。Guide 自行决定是否配文字以及配多少。讲完后，照常询问玩家是否理解这一步。
- 导师按第 6.1 节的配置运行。AI 可读英文全稿及同一玩家其他关卡的对话，以所选语言回复。引导模式围绕当前关卡目标，Regular chat 的话题由玩家决定。默认按关卡安排讲解重点：statement 关侧重对象、定义、假设和结论含义，proof 关侧重证明；这种默认不限制回答玩家实际提出的问题。不能把所有发言都解释为不理解。

### 8.6 理解确认、讨论与重新设计

- 已确认的理解不因后续提问而自动撤销。玩家再次询问基础概念可能是复习、核实细节或进一步思考；guide 应保留原确认并回应。只有玩家明确表示“刚才其实没懂”等、纠正先前确认时，才按其实际表达范围调整原来的理解状态，不能由 agent 仅凭一次提问自行撤销。若涉及已经通关的关卡，只重新帮助玩家理解相应内容，保留通关与后续解锁状态；不因玩家纠正理解确认而撤销既有进度。
- 理解与同意分别判断和记录。玩家可以已理解某段内容，同时认为其解释牵强、论证不足或存在问题；负面评价和异议不能撤销已明确确认的理解，不能要求玩家认同原文或引导者才能继续。
- 理解按钮与玩家用自然语言明确表达理解等效；确认严格按实际语义覆盖相应内容。讲解包含 A 与 B，玩家只确认 B，就只确认 B；A 仍不能默认已被看过、理解或同意。不能要求补说“我理解了”来完成旧引导，也不能因玩家的判断正确就把整张草稿判为已理解。
- 未得到按钮或等效文字确认的引导是可丢弃的“草稿纸”。玩家作出其他反映后，旧草稿在推进逻辑上作废，不压入必须返回的父步骤栈、不积累待确认任务，也不自动重播或追回旧解释。对话历史可以保留供理解上下文，但不能成为必须让玩家逐层通过的教学树。已明确确认的局部理解仍保留，玩家反映保留在正常对话中。丢弃的是旧的讲解方式，不是完成当前关卡所必需的内容。若旧稿包含 A 与 B，而玩家只涉及或确认 B，agent 仍负责自行判断何时以重新设计的方式带到必要的 A；不能恢复旧草稿或把 A 变成要求玩家补确认的旧账。
- 未确认时必须考虑玩家可能根本未读这次引导，不能默认其已读完后才表示不理解。讲解包含 A 与 B，玩家只对 B 发表意见，就不能由其对 A 的沉默推断阅读、理解或认可；后续安排应按玩家可能完全未看 A 处理。仅展示过内容不是阅读证据。
- 玩家没有确认而给出反映时，agent 应立刻放弃让玩家通过旧步骤的目标，退一步重新思考更基础、更合适的切入点和认知跨度，根据最新讨论重新生成一小步；不原样重复、不沿旧解释强行分层直到玩家完全接受。重新设计由 agent 自己承担，实在无法判断时才询问玩家，不把教学设计工作交给玩家。
- 尊重玩家的疑问、批评、判断及推进意愿。判断正确时明确同意并继续；有异议时开始真实讨论，可以修正引导者自己的解释。双方说清并同意“这个直观牵强或解释不足”已经是清楚的讨论结果，不等同于“仍未理解，只好搁置”。共识不必与 manuscript 一致。若仍有分歧，提出保留双方观点与理由、在对话中保留这条反映后继续，不以消除分歧或玩家完全同意为条件。
- 每次回应仍是一小步尝试，并邀请玩家确认当前这一步；不另设先完成全部讨论、再重新进入引导的固定阶段。理解目的说明应简短自然，不另出技术测验，也不压缩复述整段解释。禁止考试或要求展示答案作为理解证据。
- 发现论文解释不足或数学问题时，指出并记录；不在游戏中与玩家开展论文改写或证明修复。为讲清为什么有问题，可以给出反例或正确的概念解释；这属于帮助理解问题，不等于修复论文。发现实质漏洞后，向玩家说明可反馈的问题及定位，保留在本地对话和存档中。讲清后不继续寻找替代证明或改写原稿，左侧面板仍展示原始材料。讨论可用于澄清原文和双方判断，但不把游戏变成修改原研究或推进证明的工作流。若双方确认正式论证存在错误或缺口，玩家理解了原来的论证思路、问题位置以及为什么构成问题，就可以确认完成本关；将问题保留在游戏对话与存档中，供后续论文迭代参考，不在游戏中修复，也不以等待修好作为通关前提。
- 当本关必要内容已谈清且相应理解已由玩家确认时，guide 应主动做简短收尾，说明这一关已经讲清，并邀请玩家通过理解按钮或明确文字确认通关；收尾应忠实于实际讨论结果，包括已说清的局限、问题或保留的不同判断，不把它们改写为玩家同意原文。最后仍由玩家确认，不能由 agent 自动通关，也不增设最后考试。
- 每个关卡左侧底部保留 I understand this convention / statement / proof 按钮。玩家可自行确认整个关卡，即使未走完引导也能通关；通关后返回地图。当前一小段的确认与整个关卡的确认不同。玩家明确说“这一关已经理解了”等、实际语义覆盖整关时，与点击整关理解按钮等效，直接通关，不要求再补点按钮。关键是玩家明确确认及其实际范围，不是确认形式；仅确认局部内容不能扩大为整关确认，AI 自称完成不能代替玩家确认。
- 玩家可以按操作发生的逆序逐步撤回，跨关卡一直退到本次游戏的初始状态。每次撤回恢复上一步操作前的对话、理解确认及由该操作改变的通关和解锁状态。撤回旧操作时，先依次撤回它之后的操作。撤回提问时，取消尚在生成的回答或移除已生成的回答，并把原提问放回输入框供编辑。撤回后的内容从活跃对话上下文中移除，手动存档各自保存原有进度。

### 8.7 游戏状态下载与上传

- 取消独立的后台“用户反映”采集、整理或提炼流程，保留游戏正常的对话历史与学习状态。后续如何利用这些交互修改论文，不属于游戏自动化流程。
- 界面提供游戏状态的下载（导出）和上传（导入）操作，作为玩家可主动使用的存档方式。这里是本机游戏状态文件的导出和读取，不要求云端托管或向第三方发送存档。
- 提供手动存档按钮，每次操作都新增并保留一条独立存档记录，不覆盖已有手动存档。各条记录分别支持载入、下载或删除。手动存档不只是下载文件，也提供本机可恢复的进度；后续游玩不能改写或消除这一已保存进度。载入按下述替换语义恢复；下载导出所选存档，而非悄悄改为当前进度。
- 存档应包含足以接续游玩的完整游戏状态，包括进度、对话、按实际范围确认的理解及每关模式。上传读取相应存档并恢复，以存档状态替换当前状态。游戏在本机自动保存，支持重启恢复和手动存档、返回及下载。恢复或导入替换前保留原状态的可恢复备份。存档仅可导入同一脚本快照的游戏。遇到不同快照的存档或无效文件时，保留当前状态并说明原因。
- 自动存档、手动存档和导出的存档均包含截至保存时的逐步撤回历史。载入或导入时一并恢复该历史，玩家可以撤回保存前的操作，直至该次游戏的初始状态。
- Guide 的插图和 Regular chat 按玩家要求绘制的图直接显示在对应回复中，并随对话保存。导出的存档须包含图片本身。玩家重访关卡、重启游戏，或在另一台电脑导入存档后，都能在原来的回复中看到同一张图。
- 用户提出 Git 可作为存档版本管理的实现思路；需求规定可保存、返回、下载和上传替换的行为，不固定底层存储技术。
- 玩家可将导出的完整存档交给后续论文迭代流程，间接提供实际交互中的反映；游戏不额外生成用户反映报告、分析意见或自动启动论文生成，也不修改稿件与数学审查状态。

### 8.8 预备响应与连续性

- 引导展示当前步骤时，可以后台准备玩家点击理解后的下一步；关卡开放时也可提前准备引导开场，减少进入引导的等待。玩家已选择 Regular chat 时，后台预备不因此切换模式或显示引导讲解；预备不算玩家互动、确认或通关。
- 已准备好则直接复用；仍在准备时等待同一次请求，不重复生成。玩家提问或上下文改变时，丢弃不再适用的预备结果。离开页面或阅读时间长本身不应让有效结果过期。离开、返回或重访页面本身不是新的用户反映，不另设教学推进、重写或补确认流程；等待玩家实际按按钮或发送对话，再按该次行为的语义处理。
- 每个关卡的两种模式分别显示、分别保存对话记录；智能体可以参考另一模式的对话以理解玩家的问题和已有背景。保存和恢复模式选择、两种对话历史、按实际范围确认的理解及继续所需的对话上下文；不恢复旧的父步骤确认债务。另一模式的聊天不自动构成引导理解确认，但其实际内容可以帮助设计新的引导。

### 8.9 本机运行与费用

- 游戏内对话接入玩家自己的 Codex。进度和关卡对话保存在各自本机，关闭后可以继续。静态网站托管即可分发游戏。
- 玩家必须使用自己的 AI 账号或访问凭据，并承担自己的模型费用或额度消耗，作者不提供代付。凭据方式不强制限定为 API key；须使用实际受支持的连接与登录机制。
- AI 导师使用联网推理。从分享链接启动本机游戏的链路、指定模型可用性、网页对话连接与本机存档恢复，均须在实施中实际验证。按实际验证过的环境报告兼容性。

### 8.10 GitHub Pages 链接分发

- 游戏网站部署到 GitHub Pages 后通过链接分发。游戏页面及部署文件不包含外部参考文献的 PDF、文本、转录或 Markdown sidecar，也不附带审查记录、原始上传文件或玩家存档。外部引用直接链接到实际引用版本的 DOI 页面。无 DOI 时使用出版社或官方存档的稳定页面。保留书目信息及已核验的定理号、章节或页码。游戏正文保留脚本自身对外部结果的表述和用法。
- 玩家打开游戏链接后，从 GitHub Pages 复制启动提示词给 Mac 上的 Codex。启动器取得 GitHub 上的固定发布版，下载并核对游戏数据，在本机启动或复用同一游戏服务。服务就绪后由 macOS 默认浏览器打开实际本机地址，启动器也输出该地址供重开或在另一个浏览器访问。
- 分享页在复制按钮前说明为什么使用桌面 Codex、提示词会执行的操作、导师使用的账户及进度保存位置。玩家可以先展开查看完整提示词和该版本的启动器源码。
- 同一个本机地址中的各标签页及浏览器共享同一游戏和本机存档。启动流程只需要游戏清单网址，连通性不依赖从 GitHub Pages 到本机的跨站网页请求。导师使用玩家自己的 Codex 登录及用量。验收实测默认浏览器打开实际端口、重开后恢复进度、重复启动复用游戏，以及公开部署文件只通过外部链接提供文献出处。

## 9 `writer` 稿件与报告生成

`writer` 是引导模式的内部交付阶段，由引导模式按当前脚本的验证结果或第 9.4 节的撤回决定调度。

### 9.1 启动与交付

- 完整稿件生成仅适用于用户自己的未公开数学项目。开始时只读核对交付快照和当前审查记录，快照内所有组件均须在审查范围内且为 safe，当前版本没有尚未闭合的目标义务或待探索内容。引导模式从自动化脚本验证最终通过的同一份快照启动 `writer` 和游戏导出，可以并行。
- 每轮生成一份完整英文数学稿件，交付实际编译的 PDF、可独立编译的 LaTeX 源码与资源。省略作品标题和作者署名。流程省去作者说明、AI declaration 模板、红队和模拟投稿，写作完成后由 Writer 自查并验证编译、交叉引用及文档内容。
- Writer 按已验证的交付快照写成一篇完整稿件，覆盖当前 Main Results 中的全部目标定理及其证明。普通改写错误由 Writer 对照脚本纠正。生成期间脚本及审查状态只读。
- 主动查找脚本中的数学错误由前置验证角色负责。Writer 和游戏制作者以通过验证的脚本为依据，分别检查稿件是否忠实于脚本，以及译文和游戏网站的质量。若在完成这些工作时碰巧发现共享英文脚本存在影响目标或核心结论的实质数学问题，记录具体位置、依据与影响，暂停所有依赖该脚本的交付，由主 agent 自动将问题交回验证流程。修复并通过适用的数学复审和收尾审查后，从同一份新验证快照重新生成受影响的交付物。
- 若发现问题时已有受影响的产物交付，主 agent 向用户说明对应版本和具体问题。复审通过后交付重新生成的产物，并注明它所替换的版本。

### 9.2 数学与写作质量

- 面向论文大领域的高年级博士生。保留主结果的准确强度、范围、必要假设及已验证的证明路线。可以自主安排章节、记号、定理、正文和附录，可合并重复论证或把辅助引理并入证明。正文、附录与经核实的引用共同给出完整推导，读者可脱离原始研究笔记阅读。
- 非平凡步骤须交代理由，解释关键思想并保留必要数学细节。有实质数学内容的定义、条件、结论和推理若可同时用自然语言和公式表达，应同时给出且含义一致。简单记号无需机械重复。省略真正例行的计算，篇幅按数学内容与读者所需决定。
- 引言先从目标读者熟悉的具体事实自然引出问题，充分说明已知进展、真正困难、解决方法和本文实际解决的范围；然后严格陈述主要结论，事先给出所需定义、记号和假设；最后讨论相关文献。问题链以实际数学联系为准，不要求固定数量或形式。贡献表述准确、充分且克制。
- 核实所有来源和已有结果的描述。解释专门技术是什么、为何适用及如何使用。改写后保留仍被实际使用的文献与归属，对已移除且无其他用途的材料可删相应引用。项目已有反馈可作为参考，保持范围、数学结论和已验证路线。

### 9.3 默认 TeX 形式

- 文档类使用 `amsart`，字号为 `12pt`，纸张为 A4；使用 `geometry` 宏包将上、下、左、右页边距均设为 `1in`。
- 参考文献使用 `amsrefs`，条目直接保存在论文 TeX 文件中，不使用单独的 `.bib` 文件。此要求不限制正文按章节拆分为多个 `.tex` 文件，不要求整篇论文只有一个 `.tex` 文件。
- 定理、引理、命题、推论、定义、注等定理类环境共用计数器，按 section 编号；公式使用独立计数器，也按 section 编号。
- 仅给需要引用的公式编号，默认使用 `mathtools` 的 `showonlyrefs` 功能自动实现；公式引用统一使用 `\eqref`，配合 `\numberwithin{equation}{section}`。实际编译须使交叉引用与编号稳定。
- 启用可点击的交叉引用与参考文献链接，默认使用 `hyperref` 的 `hidelinks` 设置，链接为黑色文字、无边框。

其余沿用 `amsart` 默认样式，用户明确指定的格式可覆盖默认值。

### 9.4 公开文献审稿报告

- `writer` 交付实际编译并检查过的 PDF 审稿报告。完成编译后核对 PDF 中的数学公式、引用与原文定位。
- 公开文献项目的脚本验证通过后，`writer` 生成通用英文 referee report，无需设定目标期刊。Writer 在内部逐项对照最初选定的目标原文和用于游戏交付的同版验证快照，覆盖活跃目标定理及其原文论证，并使用已完成的多智能体审查作为证据。
- 报告面向作者，只评议原始稿件。说明原文版本、贡献和审查范围，将具体意见定位到原稿。报告不提及游戏脚本、另一个稿件版本或内部比较过程，也不给出接收、小修、大修、拒稿等编辑处理建议。
- 未确认原稿有数学错误时仍交付报告，评价主要结果及其数学价值，给出影响理解或核查证明的具体建议，同时写出有依据的用词、符号及行文方面的小建议。
- 对经第 6.5 节确认的问题，依据项目内的 `report.md` 写出原文定位、可核查的依据和受影响的结论，覆盖最终脚本已移除的原文论证。完整替代证明留在内部。交付前按原文和最终脚本核对内部比较及报告中的数学判断。
- 若 Writer 在整理报告时碰巧发现支撑必要绕道的反例有误，主 agent 暂停报告和游戏的待交付工作，把反例及受影响的证明路线一并交回自动化脚本验证。重新核验原文是否有硬伤及绕道是否仍有必要，按修订结果完成适用的数学复审和同版收尾审查，再根据复审结论继续交付。若受影响的游戏版本已交付，按第 9.1 节通知用户并交付需替换的版本。
- 若原目标定理因反例经用户确认修订，报告给出原结论和反例，并将经核验的修正结论表述为对原文的修改建议。
- 核心错误尚无法修复时，第 6.5 节的项目报告和 `refactor` 用于向用户说明问题并保存进度。若用户确认撤回最后一个目标定理，`writer` 根据目标原文、已核验的反例和撤回记录生成硬伤报告。交付物只有这份报告。核对原结论、反例、原文定位和撤回决定，报告通过检查并交付后完成引导任务及同一 Goal。
- 若复核确认撤回定理所依据的反例不成立，且没有其他已核实的撤回依据，回到 `refactor`，向用户说明反例错在哪里。由用户决定恢复验证还是维持撤回。

## 10 实施验收和维护

- 运行说明、实际角色输入、审查隔离、版本绑定、状态更新与测试须一致。数学结论由相应角色作可核查的判断，结构校验、编译或 hash 不替代数学审查。
- 使用独立新会话验证正常通过、实质缺陷拒绝、修复后重新审查、旧版本结果拒收、缺失来源等待与恢复、累计计数、超过旧轮数仍能继续、审查范围正确及目标定理修改须经确认、文献复用通过以及失败保持旧成果。
- 用两类项目验证完整引导链。另行验证主会话首次检查更新、有更新时暂停征求确认，以及各内部会话统一使用主会话为本次任务选定的版本。覆盖目标版本公开日期、截止日期后来源被排除、常规审查独立、公开文献的路线不符触发调整和同版双重复审、未公开项目简化回退、`writer` 项目限制和两项交付读取同一验证快照。
- 验证一次引导启动即可自动走完正常流程，且同一 Goal 持续到全部适用交付物通过检查。单独验证脚本时，核对 Goal 在同版收尾审查通过后完成。覆盖阶段报告后自动继续、可恢复问题处理后接续，以及并行交付中一项受阻时另一项继续。
- 验证游戏与稿件各自通过检查后分别交付。分别覆盖 Writer 和游戏制作发现英文脚本实质数学问题的情况，核对受影响的交付同步暂停并自动退回复审，通过后均从同一份新快照重新生成。若已有产物交付，核对用户收到受影响版本的说明及替换版本。译文本身的错误在游戏导出阶段修正并复查。
- 验证公开文献项目在脚本通过后自动编译、检查并交付独立的 PDF 审稿报告。覆盖有和无原文硬伤的情形，核对内部比较覆盖各活跃目标，PDF 只评议原稿且符合第 9.4 节。核心错误无法修复时，核对项目记录和 `refactor` 交接。用户确认因反例撤回最后一个目标定理时，核对仅交付 PDF 审稿报告，并在报告通过检查并交付后完成 Goal。
- 验证未公开项目经用户确认撤回最后一个目标定理后，保存现有工作和撤回决定，向用户说明原因后结束任务，且交付止于该说明。
- 在 ChatGPT Work 和 macOS 上验收制作流程，在 macOS 上验收游戏运行。游戏验收覆盖第 8.10 节的本机端口启动、公开文献首页的原论文标题和作者及版本、外部引用链接及定位、公式与关卡导航、双语切换、真实导师调用、本地恢复、手动存档导出与重新导入。用实际可运行的宿主与已配置模型验证，报告真实能力差异。
- Proof2Game 的需求以本文件为准。运行时说明和实现记录单独维护。已确认的要求直接用于实现，有实质冲突或新的用户可见差异时再讨论。运行工具参数、路径或交接错误由执行方纠正，同时防止伪造执行结果或手改状态绕过审查。
