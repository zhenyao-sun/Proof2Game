# Mathematical worker contracts

Use this reference for creating or continuing a worker. The main coordinator follows [verification.md](verification.md). Use [roles.json](roles.json) for defaults and apply explicit project overrides by role. Explorer and Interface Optimizer use the same `explorer` configuration and session. Keep `simplification` and `public_route` independently configurable. Dispatch on the host using actual supported model and reasoning parameters. Confirm the current main session's configuration through host or launch evidence. Prompt text cannot change or establish a session's model. If the host cannot use or confirm a configured model, reasoning level, independent session, or required continuation, report the capability gap and preserve work. A user may explicitly choose a supported override.

The coordinator assembles each worker's applicable instructions and needed materials, supplies the version selected by the main session, and records the host session identity, model, reasoning level, operation, and exact input binding. Workers use that selected release. They skip release discovery. Use fresh independent contexts with no forked author or coordinator conversation wherever a fresh session is specified. Keep prior reviews, Fixer judgments, other workers' findings, and the expected answer out of review packets. Ask for precise locations, evidence, and concise checkable reasons. Reissue malformed requests to the same worker where possible. No role gets to approve its own revised mathematics by assigning a safe classification.

## Reviewer

One fresh Reviewer per component per round, up to ten concurrently, and the same reviewer for the component's successive gates. Send only the current gate and its allowed materials. Each component can advance independently as capacity permits. Stop that component's round at its first substantive `nonpass`. Optional polish never blocks. Return `pass` when the gate finds no substantive defect, `nonpass` with the actionable defect and its evidence, or a source wait when a required input for that gate is missing. Record each result as an English mathematical finding. The reviewer describes problems and can suggest a repair without owning implementation. The Statement, Convention, and Proof verdicts remain separate.

For each current ledger assignment, run `python3 scripts/review_dispatch.py --task <task-directory> --token <current-token>` from the skill directory. Check the returned version, model and effort, then pass the returned **message** to a fresh un-forked Reviewer or the specified continuing session. Keep the detached packet separate from project and ledger files. Record the actual host session, and check the returned token, snapshot, component, gate and packet SHA-256 before accepting the result. Source-blind gates return `pass` or `nonpass` and can raise packet delivery problems separately with the coordinator. Only source-enabled gates return `waiting-source`, identifying the missing external work and its use. The script verifies the packet contents; the coordinator retains responsibility for actual host isolation and evidencing results.

### Input boundary

- Supply exact current component content, complete effective ambient conventions, and only the direct Statement interfaces needed for the gate. A Proof also receives its exact paired Statement. The Convention opening exception below receives a prefix. Preserve ordering and relevant mathematical notation in these packets.
- The text, decomposition, self-containment, and correctness gates are source-blind. Exclude external documents, OCR, search results, summaries, and source access instructions, even if the coordinator already gathered material. Tell the Reviewer to use only its detached packet during those gates and to defer external reads. Provide any later allowed source evidence only after earlier passes. Treat a fully stated external interface as a provisional assumption during internal correctness, and check how the current manuscript uses it. No later source material may excuse an earlier defect.
- Packets must have actual allowed text and give no broad project link, inherited chat, state log, or deeper dependency traversal. A path or sibling file in a shared checkout grants no additional reading permission. Describe this as scoped worker input, with only the access controls the host actually provides.
- For public-literature projects tell the ordinary Reviewer, “Judge this manuscript independently. The target publication must not influence your mathematical judgment.” Keep its route and published status out of that judgment. The source gate can consult narrow evidence needed for a cited interface under the same source rules. The independent end-of-run route reviewer has a different remit and receives the actual target edition.
- All validation roles use only external evidence eligible under the exact target version's publication cutoff for a public project. See [intake.md](intake.md) for evidence, references-first lookup and version selection. This restriction covers later results and techniques, including corrigenda, even when familiar to the worker.

### Statement gates in order

1. **Expression and readability.** Include the actual immediately preceding mathematical prose or component and any intervening transition, alongside the current opening and complete Statement. Require the minimum mathematical transition needed when objects or tasks change. Check that result kind and optional title are accurate and the reader-visible proof locator identifies the real proof. This is a local continuity check.
2. **Self-containment.** Require a consumable specification across the surrounding prose and formal environment. Check domains, assumptions, quantifiers, scope, variables, normalization, and stated external interfaces.
3. **Mathematical correctness.** Check well-formedness, conditions, notation, legitimate contextual instances and logical content of the Statement. Proof existence and correctness belong to the separate Proof review. The source/reuse checks may inspect the existing paired proof only to locate specialization and applicability arguments.
4. **External sources.** Verify the cited interface by direct inspection of the correct, eligible original PDF, including conditions and scope. A narrow paired-proof check can locate evidence about applicability. The Statement still supplies its own complete interface.
5. **Literature reuse.** Use the common rule below. The same limited paired-proof inspection applies.

### Convention gates in order

1. **Opening orientation.** Include only the section-like title, adoption text, full inherited settings, prior Statement interfaces explicitly referenced there, and the first nonempty paragraph. Withhold the rest of the Convention, the preceding section's technical ending, proofs, and later pages. A first-time sequential reader should be able to tell what new object, tool or construction is introduced, why it appears here and its rough role. A clear title and inherited context may suffice. Use inherited definitions as known background.
2. **Full expression and readability.** Supply and inspect the complete exact Convention only after the opening passes.
3. **Self-containment.** Require the complete local interfaces, definitions and standing hypotheses used by downstream components.
4. **Mathematical correctness.** Check consistency, notation, scope, definitions, and actual use of inherited settings. Flag nontrivial claims that require a dedicated Statement and Proof. The responsibility here is the new Convention, including any conflicts or invalid inherited instantiation.
5. **External sources.** Verify cited mathematics and the existence specifications, including one common witness where consumers need to share one.
6. **Literature reuse.** Use the common rule below.

### Proof gates in order

1. **Expression and readability.** Check that the mathematical argument and necessary navigation are readable without guessing.
2. **Proof decomposition.** Check whether actual mathematical stages, reductions, independent claims and dependencies are legible. Extract a meaningfully separate claim into its own Statement, Proof and proof node when needed. Length alone gives no threshold.
3. **Self-containment.** Require the mathematical inputs needed to read and apply the steps, with actual interfaces and contexts.
4. **Mathematical correctness.** The paired Statement is the obligation. Verify all nontrivial steps, actual dependency applicability, coverage and edge cases, circularity, limits and interchange, convergence and uniformity. A uniquely mechanical inference with no hidden condition may remain implicit. A nontrivial gap requires an argument in the manuscript even if the reviewer knows one.
5. **External sources.** Check the exact original PDF against the specific use and instantiation. Routine background may need no citation. Verify new applications of a cited result to new parameters, objects, or hypotheses.
6. **Literature reuse.** Use the common rule below.

### Source and reuse decisions

Investigate specific opportunities to avoid a nontrivial repeated derivation. A formal conclusion needs the actual original PDF. Preserve full provenance and exact locations. A reuse nonpass requires a current unresolved attribution, relationship to known work, or needless derivation with evidence. Relevant overlap already correctly attributed or handled by a proper application and genuinely needed extra work may pass. In public-literature projects, overlap alone permits retaining the original target argument. Concrete bad attribution, invalid application, and mathematical defects remain reviewable. Record which issue is actually present. Preserve standard attribution, and require nontrivial bridging work in the paired proof. For `sources` or `reuse` pass, record a `sources` array with the verified `id` and `sha256` and applicable `locators` for each source, or `[]` if none applies. Use the project reference identity and physical PDF page locators described in [intake.md](intake.md).

For a missing exact PDF, return a source wait with the reference's stable project work key as `source`, `source_version` when the exact edition is known, and the mathematical location and required flag. Identify the publication and result in the evidence. Apply the coordinator's saved user resolution under [verification.md](verification.md). A dependency on nonpublic material is a substantive source issue to resolve with a verified public source or a self-contained argument. Reviewers should read the adopted public original directly. Material available under subscription qualifies once it is lawfully obtained and verified.

## Batcher and Fixer

The **Batcher** is fresh per round. After every review in the round has ended, group every accepted finding by repair relationship, retaining its ID, wording, locations and evidence. Check one-to-one finding coverage in the handoff. The same **Fixer**, fresh when that round begins fixing, handles all batches serially. Give it the entire issue list before writing. It may resolve later findings by an earlier fix, determine a finding is moot after a route change, restore a discarded dependency, choose a better rigorous repair, or record a justified disagreement. Record a disposition and reason for each finding against the current staged draft. Batching neither repairs nor edits verdicts.

The Fixer independently verifies diagnoses, causal assumptions and proposed edits. Use rigorous mathematical and structural judgment for proofs; use ordinary editing judgment for wording or navigation. A substantive fix may affect dependencies, consumers, conventions, proof trees and assembly, and may reach outside the current review range. Respect target meaning, pairing, order, references and public route constraints. Preserve unresolved obligations as issues. A new claim requiring proof needs an actual proof. Report a blocker only after a reliable mathematical repair cannot be found or a necessary decision exceeds the Fixer's authorization. Pure readability disputes remain unsafe for a fresh reviewer. A reasoned clarification of otherwise sound text can reduce misreadings. Its old nonpass remains a recorded nonpass.

In public-literature projects the Fixer consults the exact target version at the relevant original argument, follows the original core route where sound, and runs any necessary departure through the hard-error procedure. It may annotate uncertainties without elevating them to confirmed errors. Verify the counterexample or other evidence before asserting an original defect, and use a documented detour only as allowed in [verification.md](verification.md).

If the active Fixer session is lost, supply a fresh Fixer with the full finding list, staged candidate, and prior dispositions. It checks and retains valid completed changes, then resumes the remainder. If an active Reviewer is lost, replace it for that component and restart at the first gate. Keep all other still-valid findings and passes. Preserve actual session identities and supersession in the project record.

## Explorer and Refactor implementation

Use one fresh **Explorer** for each exploration and reuse it for that invocation's optimizer. Inspect the actual union of the dependencies of every current target, plus pairings and applicable conventions. For each newly in-range or returning interface, try a weakening with a substantive reduction in proof burden only when every current direct use still works. If multiple edits affect one proof, verify the combined candidate. Under the public cutoff, read the selected target edition and preserve a traceable core route. A discovered possible error in a component about to be included can receive one opportunistic repair attempt. Failed attempts leave the original component for ordinary review. The assignment is dependency discovery and interface optimization. Every admitted item starts unsafe.

A **Refactor implementation worker** starts fresh after the user and main have agreed on the manual refactor or after the main accepts an internally authorized route plan. Give the worker the actual scope and confirmation, if required. Have it stage one coherent change against the bound start version. New decisions or infeasible agreed actions return to the same main conversation with concrete evidence. Any proposed change to a target's mathematical meaning needs separate user confirmation of that actual change.

## End-of-run reviewers

The **private simplification reviewer** is independent and fresh for each route assessment or actual comparison. Supply current full proofs, obligations, the Git checkpoint, prior attempts and concrete failure/comparison history, and the working draft's discarded branches when relevant. Assess feasible mathematical route simplification, including independently verified literature when useful. Cite where proof burden would actually decrease. A valid comparison uses the completed and re-reviewed candidate and the complete pre-attempt proofs. Identify clearly simpler, clearly worse, infeasible, or genuine tradeoffs with evidence. Preserve the comparison and any failed implementation in the history for the next reviewer. The final finding of no feasible further simplification applies only to the reviewed script version.

The **public route reviewer** is independent and fresh for every review. Supply the precise current approved mathematical draft, its proof-closure evidence, the fixed source edition with locators, and the relevant hard-error and target-confirmation record. Trace key reductions, estimates, constructions and interfaces to the original where sound. Equivalent wording, reordered arguments and filled-in omitted steps are permitted. Overlap with other papers alone has no bearing on route conformity. For each necessary departure, confirm directly that the original hard error is real and that the recorded route change is necessary. Issue a same-version pass or precise nonpass with original and current locations, reasons and remaining conditions. Ordinary mathematics checks remain a separate result.
